## Ziel

Erste End-to-End-Scan-Pipeline ausliefern: ein externer Aufrufer
(Home Assistant, Paperless-Plugin, n8n, curl) postet auf eine
profil-spezifische Webhook-URL, die scan-bridge fährt einen
SANE-Scanner über die Schwester-Container `sane-runtime` an,
montiert die gescannten Seiten zu **einem mehrseitigen PDF** (echtes
OCR und QR-Splitting kommt erst in Phase 1.3) und lädt das Ergebnis
über die Paperless-ngx REST API hoch. Profile leben in SQLite und
sind über eine CRUD-HTTP-API les- und schreibbar — das Web-UI in
Phase 1.4 setzt darauf auf.

## Architektur (zwei Container)

- **scan-bridge** — Go-Binary auf distroless-Basis. Besitzt die
  HTTP-API, die Profil-DB, die Job-Queue, den Output-Dispatcher
  und einen selbst geschriebenen SANE-net-Client. Hält keine
  USB-Geräte und shell't nicht aus — bleibt distroless.
- **sane-runtime** — Debian-slim mit `saned` auf TCP/6566 plus den
  SANE-Treibern (nur `avision`-Backend aktiv). Hält das USB-Gerät.

Kommunikation zwischen den beiden ausschließlich über das
SANE-net-Protokoll. Beide Container produziert das Projekt
multi-arch (linux/amd64 + linux/arm64) für Pi-Deployment.

## Tech-Stack

- Go 1.22+ (statisches Binary, ARM64-Cross-Compile via
  `CGO_ENABLED=0`)
- `modernc.org/sqlite` — pure-Go SQLite (kein CGO, distroless-fähig)
- `golang-migrate/migrate/v4` — Schema-Migrationen
- `go-chi/chi/v5` — minimaler HTTP-Router
- `gopkg.in/yaml.v3` — YAML-Profil-I/O
- `getsops/sops/v3` — SOPS-Entschlüsselung (Go-API, kein Shell-Out)
- `prometheus/client_golang` — Metriken
- `docker buildx bake` — Multi-Arch-Container-Builds

## Aufgelöste Open Questions aus der Spec

| ID | Frage | Entscheidung im Plan |
|----|-------|----------------------|
| O-1 | Paperless ASN-Reservierung | Nächste ASN aus `?ordering=-archive_serial_number&page_size=1` ableiten, durch Job-Queue serialisiert (keine Race-Bedingung) |
| O-2 | OpenTelemetry-Tracing | **Verschoben** auf Phase 2.x — Phase 1.2 hat Prometheus + strukturierte Logs mit `scanId` |
| O-3 | Token-Storage | **HMAC-SHA256 in SQLite** — Profil-Tokens werden als HMAC-SHA256 unter einem daemon-weiten Server-Secret gespeichert, nie im Klartext; der Klartext wird beim Anlegen/Rotieren genau einmal zurückgegeben. Details in Δ-7 des Plans (ersetzt die ursprüngliche Klartext-Entscheidung) |
| O-4 | saned via TCP oder Unix-Socket | **TCP/6566** — einfacherer Go-Code; Container-Netzwerk-Isolation ist die Sicherheitsschranke |
| O-5 | Go-SANE-net-Library oder selbst schreiben | **Selbst schreiben** in `internal/sanenet/` — Protokoll ist überschaubar, keine Drittanbieter-Abhängigkeit, ARM64 trivial |

## Sicherheits- und Secrets-Modell

Drei Lade-Pfade, in dieser Priorität:

1. Docker-Secret-Datei unter `/run/secrets/<name>`
2. Umgebungsvariable `<NAME>` in Großbuchstaben
3. SOPS-verschlüsselte YAML-Datei (Pfad in `SCAN_BRIDGE_SECRETS_FILE`,
   age-Key in `SCAN_BRIDGE_AGE_KEY_FILE`)

Profile referenzieren Secrets ausschließlich per Namen
(`api_token_secret: paperless_api_token`). Klartext-Tokens im
Profil-YAML werden beim Parsen abgelehnt.

## Die 19 Tasks im Überblick

Jeder Task = ein logischer Commit. TDD durchgängig: erst Test
schreiben, fehlschlagen lassen, minimal implementieren, bestehen
lassen, committen.

### M1 — Foundations

**Task 1: Go-Modul-Skelett.** `go mod init`, minimal `cmd/scan-bridge/main.go`
mit `--version` Flag, `golangci-lint` Konfig, Makefile-Targets
`build-scan-bridge` und `test-go`. Liefert: ein Binary das `--version`
ausgibt und CI-tauglich ist.

**Task 2: Konfiguration und Secret-Resolver.** `Config`-Struct mit
ENV-Variablen-Loading + Defaults, `Resolver` der Secrets aus
Docker-Secrets-Verzeichnis, Env-Vars und SOPS-Datei in dieser
Priorität auflöst. `main.go` lädt Config beim Start. Liefert: ein
Daemon der mit `SCAN_BRIDGE_*` Env-Vars konfigurierbar ist.

### M2 — Data layer

**Task 3: SQLite-Schicht mit Migrations.** Embedded SQL-Migrations
(0001_init.up/down.sql), `db.Open(path)` mit
`modernc.org/sqlite`-Treiber (pure Go), WAL-Modus, Foreign-Keys an,
automatischem Migrate-Up beim Öffnen. Liefert: `Open()` legt die
DB an oder migriert sie hoch, idempotent.

**Task 4: Profil-Datenmodell.** `Profile`-Struct mit allen Feldern
aus dem Spec (Scan, Splitting, Paperless, Naming, Outputs,
Response, Metadata), Validation (rejected Felder mit Begründung),
Token-Generator (32 Byte zufällig, base64-url-encoded), Store mit
Create/Get/GetByToken/Update/Delete/List/RotateToken, YAML-Encoder
und -Decoder mit Klartext-Secret-Reject. Liefert: vollwertiges
persistentes Profil-Objekt das in SQLite landet.

### M3 — API surface

**Task 5: Profil-CRUD-HTTP-API.** chi-Router mit
`GET/POST/PUT/DELETE /api/profiles`, `GET/PUT/DELETE
/api/profiles/{id}`, `POST /api/profiles/{id}/rotate-token`. JSON
Ein- und Ausgabe. Standardisiertes Error-Body-Format. `/healthz`
und `/readyz` Endpunkte. `main.go` startet HTTP-Server mit Graceful
Shutdown. Liefert: Profile sind über curl/HA-API komplett
verwaltbar.

### M4 — Core logic

**Task 6: Tag-Merge-Engine.** Pure Funktion `Merge(defaults,
profileStrategy, callerTags, callerStrategy) []string`. Drei
Strategien (`add` / `override` / `remove`), per-Call-Override der
per-Profil-Default-Strategie. Vollständige Tabelle aus der Spec
als Test-Fälle. Liefert: deterministische, getestete
Tag-Auflösung für jeden Scan.

**Task 7: Selbst geschriebener SANE-net-Client.** Sub-Task 7A:
Protokoll-Primitiven (`writeWord`, `readWord`, `writeString`,
`readString`, `Status`-Enum). Sub-Task 7B: `Client` mit `Dial`,
`Close`, `GetDevices`, `Open`, `SetStringOption`, `SetIntOption`,
`Start`, `getParameters`. Tests gegen einen kleinen Fake-saned der
nur das nötigste antwortet. Liefert: Go-Binding ans SANE-Netzwerk-
Protokoll, ohne CGO oder externe Bibliothek.

> **Hinweis:** der Plan setzt das *Minimum* für Phase 1.2 um. Der
> komplette Read-Loop (Pages bis ADF leer + EOF-Marker im
> Side-Channel-Stream) wird erst in Task 17 fertig, weil er sich
> nur sinnvoll gegen einen echten saned testen lässt.

**Task 8: In-Memory Single-Worker-Queue.** Capacity-bounded
Channel-Queue, `Enqueue` mit `ErrFull` bei voller Buffer, `Wait`
für Sync-Aufrufer (blockierend bis Job fertig oder Context
abgelaufen), `Status` für Async-Polling, `Close` für sauberes
Beenden. Begründung: der Scanner ist eine physische Single-
Resource; Serialisierung muss eh stattfinden, und in-memory ist
für Phase 1.2 ausreichend (auch wenn Daemon-Crash bedeutet
"laufende Jobs verloren" — Caller können retryen). Liefert: stabile
Queue-Mechanik für die Webhook-Handler.

**Task 9: Webhook-Router mit Sync/Async-Hybrid.** `POST
/webhooks/<token>` schlägt das Profil per Token nach (401 bei
unbekannt), parst JSON-Body und Query-Parameter, baut den Job mit
einer Closure die das echte Scannen aufruft (per
`ScanFunc`-Schnittstelle, die in Task 11 geliefert wird), enqueued
in die Queue. Sync-Pfad blockiert auf `Wait`, Async-Pfad gibt
sofort 202 mit `scanId`. Error-Mapping (Hardware → 502, Paperless
→ 503, Queue voll → 503 mit Retry-After, Timeout-Sync → 504,
unbekannter Token → 401). Liefert: vollständig getestete
Webhook-Schnittstelle.

### M5 — Output, Stub-Processor, Metriken

**Task 10: Output-Dispatcher + Paperless-Client.** `Dispatcher`-
Schnittstelle (zukunftsoffen für Phase 2.x NFS/S3/Custom),
`Paperless`-Implementierung mit `PostDocument(file + tags + ASN +
correspondent + document_type + owner)` über Multipart-Upload an
`/api/documents/post_document/` und `NextASN()` als Fallback wenn
ASN-Mode-required ohne ersten QR steht. Auth via Bearer-Token.
Liefert: Scan-Ergebnis erreicht Paperless mit allen Metadaten.

**Task 11: Stub-Processor + Scanner-Orchestrator.** Sub-Task 11A:
`processor.Stub` der PNGs/JPEGs mit `gofpdf` zu einem
mehrseitigen PDF zusammenklatscht (kein OCR, kein Splitting —
das ist Phase 1.3). Sub-Task 11B: `scanner.Scanner` orchestriert
SANE-Aufruf, Processor-Lauf, Tag-Merge, Output-Dispatch, baut die
finale `queue.Result`. Sub-Task 11C: `main.go` verdrahtet
`productionSANE` und `productionDispatchers` (ein
`DispatcherBuilder` der pro Profil-Output den richtigen Dispatcher
mit aufgelöstem API-Token konstruiert). Liefert: Scan-Pipeline mit
Stub-Verarbeitung, alle Schnittstellen Phase-1.3-ready.

**Task 12: Health-Checks + Prometheus-Metriken.** Metric-Set
(`scan_bridge_scans_total{profile,status}`,
`scan_bridge_scan_duration_seconds{profile,stage}`,
`scan_bridge_documents_produced_total{profile}`,
`scan_bridge_queue_depth`,
`scan_bridge_paperless_uploads_total{result}`,
`scan_bridge_sane_errors_total{type}`). `/metrics` Endpoint, Counter
+ Histogram-Increments im Scanner-Pfad. Liefert: HA-Integration in
Phase 2.x kann die Sensoren direkt aus `/metrics` ableiten.

### M6 — Container

**Task 13: sane-runtime Dockerfile.** Debian-12-slim als Basis,
`sane-utils` und `libsane-extras` installiert, `dll.conf` mit nur
`avision` (Backend-Pruning), `avision.conf` mit Whitelist für
USB-IDs (i1120 + Kommentare für andere Kodak-Modelle),
Entrypoint-Skript startet `saned` im Vordergrund, Container läuft
als unprivilegierter `saned`-User. USB durchgereicht via
`--device /dev/bus/usb`, kein `--privileged`. Liefert:
schlanker Container der SANE-Geräte über TCP/6566 freigibt.

**Task 14: scan-bridge Dockerfile.** Multi-Stage Build:
golang:1.22 baut das Binary mit `CGO_ENABLED=0`,
`gcr.io/distroless/static-debian12:nonroot` als finales Image,
nur das Binary kopiert, `/data` als Volume, Port 8080 exposed,
nonroot-User. Multi-Arch-Build via buildx (`linux/amd64,linux/arm64`).
Image-Größe-Sanity-Check (<30 MB). Liefert: kleines, sicheres
Production-Image.

**Task 15: Compose-Stack.** `deploy/compose/scan-stack.compose.yml`
mit beiden Services, Docker-Secrets-Wiring für Paperless-Token,
Volume für Profile-DB, Healthcheck am scan-bridge,
`depends_on`-Reihenfolge. `.env.example` mit Image-Tags und
Konfig-Variablen. `deploy/secrets/.gitignore` der nur `.example`-
Stubs trackt. Makefile-Targets `compose-up`, `compose-down`,
`compose-logs`. Liefert: ein Befehl bringt den ganzen Stack hoch.

### M7 — Tests und CI

**Task 16: Mock-Paperless für Integrations-Tests.** Eigenes
Go-Modul unter `tests/integration/mocks/paperless/`, kleiner
HTTP-Server der `/api/documents/post_document/` mit deterministisch
inkrementierender ID beantwortet und `/api/documents/?ordering=...`
für die NextASN-Logik. Eigenes Dockerfile (distroless). Liefert:
Tests können vollen Paperless-Pfad ohne echtes Paperless prüfen.

**Task 17: Integrations-Test-Suite + finaler SANE-net Read-Loop.**
Sub-Task 17A: der echte `productionSANE.Scan` Lese-Schleifen-Code
in `main.go` — `Start` → Side-Channel-TCP-Verbinden → Page-Bytes
bis EOF-Marker (-1) lesen → nächster `Start` bis NO_DOCS, Page-Cap
bei 100 als Sicherheitsnetz. Sub-Task 17B:
`tests/integration/docker-compose.test.yml` mit scan-bridge,
sane-runtime (mit SANE `test`-Backend-Override per
gemounteter `dll-test.conf`) und mock-paperless. Vier
Bash-Szenarien (`profile_crud.sh`, `sync_scan.sh`, `async_scan.sh`,
`error_cases.sh`), Runner-Skript `run.sh`, README. Makefile-Target
`test-integration`. Liefert: vollständige End-to-End-Validierung in
~30-60 Sekunden.

**Task 18: GitHub-Actions-CI.** `ci.yml` (Push + PR auf main): Go
Lint/Test + Multi-Arch-Build (ohne Push) + Integrations-Suite.
`release.yml` (Tag-trigger `v*.*.*`): Multi-Arch-Build und Push
nach GHCR ausschliesslich mit dem Versions-Tag (kein `:latest`,
matcht die `AGENTS.md`-Regel zu pin-by-version-in-compose).
Liefert: jeder Commit testet den ganzen Stack, jeder Tag wird
automatisch auf GHCR veröffentlicht.

### M8 — Doku

**Task 19: Zensical-Doku-Seiten.** Vier Markdown-Seiten unter
`docs/site/`: Getting-Started (5-Minuten-Pfad bis erster Scan),
Webhook-Reference (URL-Format, Body- und Query-Parameter,
Tag-Merge-Matrix, Sync- und Async-Antwortformen, Error-Codes
tabellarisch), Profile-Schema-Reference (vollständiges YAML-
Beispiel, Splitting-Modi formal beschrieben, Validation-Regeln,
Phase-1.2-Limits) und Configuration (Env-Variablen, Secret-Sources,
Production-Hardening, Backup-Strategie). Liefert: Open-Source-
Nutzer können sich selbst orientieren.

- [ ] Multi-Arch-Images (amd64 + arm64) bauen in CI und werden auf

- [ ] Doku-Seiten existieren (Task 19)
- [ ] Manueller Hardware-Loop-Run am Referenz-Scanner produziert
      ein Paperless-Dokument End-to-End (Task 17 README, vor
      Release-Tag durchführen)

## Was NACH Phase 1.2 kommt (Roadmap-Hinweise)

- **Phase 1.3** — `scan-processor` mit echter Bildpipeline:
  Deskew, Blank-Page-Detect, QR-Decode (Paperless ASN-Format),
  Dokumenten-Splitting, OCR (Tesseract), Multi-Page-PDF-Assembly
  via `pdfcpu`. Ersetzt den Stub-Processor aus Task 11 ohne
  Webhook-Vertrags-Bruch.
- **Phase 1.4** — Web-UI für Profil-CRUD; konsumiert die in
  Phase 1.2 ausgelieferte API ohne neue Daemon-Endpoints.
- **Phase 2.x — Home-Assistant-Integration:** custom_component
  liest `/metrics` für Sensoren, ruft `/api/profiles/...` und
  `/webhooks/...` als Services. Schema bereits in Phase 1.2 fertig
  (Metric-Namen, API-Konturen).
- **Phase 2.x — Hardware-Trigger-Comeback:** abhängig von den
  Ergebnissen des Research-Tracks (siehe
  [`docs/research/scanner-hardware-events.md`](../../research/scanner-hardware-events.md)).
  Wenn die USB-Capture zeigt dass der Start-Button-Press auf der
  USB-Schiene erscheint und ein Upstream-Patch am `avision`-Backend
  machbar ist, kommt scanbd als zusätzlicher Webhook-Caller zurück
  in den Stack.
