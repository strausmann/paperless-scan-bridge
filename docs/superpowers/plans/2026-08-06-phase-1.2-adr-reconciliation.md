## Why

The plan (2026-04-30) predates the ADRs (backfilled 2026-06-28, merged in #11)
and the Phase 1.1 code. Two load-bearing decisions in the plan contradict now-
accepted ADRs. The maintainer chose to **align the plan to the ADRs** rather
than supersede them.

## Decisions

### D-1 — Trigger endpoint: canonical `POST /scan`, not per-profile webhooks

- **Governing ADRs:** [0005](../../decisions/0005-trigger-agnostic-scan-endpoint.md)
  (Accepted), [0006](../../decisions/0006-auth-model.md) (Accepted — auth model).
- The single canonical trigger is **`POST /scan {profile}`** with **bearer-token
  auth** (SHA-256 hashed at rest per ADR 0006). Every trigger source (Home
  Assistant, Paperless button, n8n, curl, future ESP32 panel #9) is just an HTTP
  client of this endpoint.
- The plan's per-profile **`POST /webhooks/<token>`** router is **not** built in
  Phase 1.2.
- **Rationale:** uniform interface, no per-source core code, and the bearer lives
  in the `Authorization` header — not in the URL path, where it would leak into
  access logs, proxy logs, browser history, and `Referer`.

### D-2 — Per-profile token kept as *optional* authorization layer (O-3)

- The per-profile token concept from spec open question **O-3 survives**, but as
  an **optional second authorization check** layered on top of the daemon bearer,
  **not** as the primary/only auth and **not** embedded in the URL.
- Storage stays as decided in O-3 / Δ-7: **HMAC-SHA256 under a daemon-wide server
  secret**, never plaintext; the plaintext is returned exactly once on
  create/rotate.
- New ADR [0015](../../decisions/0015-per-profile-token-optional-authz.md)
  records this and its relationship to 0005/0006.

### D-3 — Webhook trigger deferred as a *future additional* option

- A per-profile webhook-style trigger remains a **desirable future add-on**
  (kept open, e.g. for webhook-only callers that cannot set headers), but is
  **out of scope for Phase 1.2**. When it lands it will be an *additional*
  client of the same scan action, consistent with ADR 0005 — not a replacement
  for `/scan`.

### D-4 — Transport: HTTP over a Unix socket, not TCP/6566 SANE-net

- **Governing ADR:** [0009](../../decisions/0009-bridge-sane-unix-socket.md)
  (Accepted), consistent with [0008](../../decisions/0008-sane-runtime-owns-scanner.md).
- `scan-bridge` dispatches to `sane-runtime` via **HTTP over a shared
  Unix-domain socket** (named volume) — **no open TCP port**.
- `sane-runtime` gains a **small HTTP wrapper** that owns all SANE specifics
  (device open, options, the multi-page read loop). `scan-bridge` becomes a
  **plain HTTP client** over the socket.
- This **reverses plan O-4 (TCP) and O-5 (hand-rolled SANE-net client)**. The
  `internal/sanenet/` package and the SANE-net wire protocol are dropped from
  the bridge.
- **Rationale:** no listening port (smaller attack surface, matches
  `THREAT_MODEL.md`; `saned`-over-TCP has weak host-list auth), a simple HTTP
  client instead of the plan's riskiest/least-testable pieces (SANE-net binary
  protocol + read-loop), and a clean ownership boundary (`sane-runtime` owns the
  scanner, per ADR 0008). **Trade-off:** we write and maintain the HTTP wrapper
  in `sane-runtime` instead of using stock `saned` unchanged.

### D-5 — Router & layout: keep stdlib `net/http`; align package names

- Keep the existing stdlib `net/http` pattern-mux (Go 1.25). **Drop the
  `go-chi/chi/v5`** dependency the plan assumed.
- Reconcile the plan's package names (`profile`, `sanenet`, `queue`, …) to the
  existing tree (`profiles`, `dispatch`, …). Add the scan-HTTP client under the
  existing `internal/dispatch` package rather than a new `internal/sanenet`.
- Retag the current stubs from `TODO(phase 1.4)` to Phase 1.2 as they are
  implemented.

### D-6 — Profiles stay declarative YAML in Phase 1.2; DB + CRUD deferred to 1.4

- **Governing ADR:** [0010](../../decisions/0010-profiles-declarative-yaml.md)
  (Accepted). Scan profiles are **named YAML entries, strictly validated at
  daemon startup** (unknown fields rejected; daemon refuses to start with zero
  profiles) — exactly what `internal/profiles` already does.
- The plan's **SQLite profile store + write CRUD API** (`POST/PUT/DELETE
  /api/profiles`, rotate-token endpoint) is **deferred to Phase 1.4**, when the
  management web UI lands — this is ADR 0010's own stated follow-up, not a new
  idea. Phase 1.2 keeps the existing **read-only** `GET /profiles` /
  `GET /profiles/{name}` surface plus reload-from-YAML.
- **Consequence for Phase 1.2:** likely **no SQLite at all** — the queue is
  in-memory (Task 8) and profiles are YAML, so nothing in the 1.2 scope needs a
  database. Drop `modernc.org/sqlite` and `golang-migrate` from the 1.2 stack;
  reintroduce them in the Phase 1.4 DB work.
- **Interaction with ADR 0015 (optional per-profile token):** the token *model*
  (optional second authz, hashed at rest) holds, but its **management surface**
  (create/rotate returning plaintext once) rides with the DB/UI in Phase 1.4.
  In Phase 1.2, an optional per-profile token — if used at all — is
  **declarative**: a hash in the YAML profile or a secret referenced by name and
  resolved via the secret resolver, validated at startup. No runtime rotate API
  in 1.2.

## Acceptance criteria (amended)

Same as the 2026-04-30 plan, except:

- End-to-end criterion reads through **`POST /scan {profile}` + bearer**, not a
  per-token webhook URL.
- The bridge ↔ `sane-runtime` hop is exercised **over the Unix socket**; no TCP
  port is opened by either container.
- Per-profile-token authorization (optional layer) has at least one test.
- **Dropped for 1.2:** "profile creatable via CRUD API" — profiles are
  declarative YAML (D-6); the write CRUD acceptance moves to the Phase 1.4 DB
  work. Phase 1.2 asserts profiles load and validate from YAML at startup.
